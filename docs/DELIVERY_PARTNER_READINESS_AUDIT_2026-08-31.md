# تقرير جاهزية بوابة شريك التوصيل — وصلة

تاريخ الفحص: 31 أغسطس 2026. النطاق: استقبال أول شركة توصيل؛ المطاعم مؤجلة.

## القرار التنفيذي

**غير جاهزة حالياً لتشغيل طلبات حقيقية مع أول شركة بصورة مستقلة وآمنة.**

يوجد أساس يعمل: تسجيل شريك، دخول، مراجعة الإدارة ونشر التطبيق، تفعيل التاجر، إنشاء الشحنة عبر HTTP، واستقبال حالات موقعة. لكن هناك عوائق في نسخة النشر، المناطق، الصلاحيات، وإدارة تعطل الشريك وترتيب الأحداث. المطلوب إصلاحات محددة، وليس إعادة بناء المنصة.

- 37 اختبار قبول مخصص: **21 ناجحاً، 16 لم يتحقق**. هذه معايير قبول، وليست نسبة جاهزية تجارية ولا بالضرورة 16 علة مستقلة.
- 297 اختباراً قائماً في 54 ملفاً: ناجحة.
- فحص TypeScript: ناجح بعد إعادة توليد أنواع المسارات وإزالة ملف تحقق مؤقت تالف داخل `.next/dev/types`؛ لا تعديل لكود التشغيل بسبب ذلك، ولم يُنفذ بناء إنتاج كامل.
- 34 migration: طُبقت بنجاح على PostgreSQL محلي جديد؛ لا يعني ذلك فحص قاعدة الإنتاج أو نسخها الاحتياطية.
- فحص بناء Docker مصغر: أثبت استبعاد صفحة المناطق من سياق البناء.
- لم تتغير بيانات الإنتاج أو إعداداته أو مفاتيحه، ولم يُنشأ شريك وهمي منشور في الإنتاج. لا commit أو push أو deploy في هذه المراجعة.

## نطاق الأدلة وحدودها

الإصدار الذي أبلغ عنه `/api/health` الحي هو `576a6c8937e910a896ed0fff0551a34499b1d8d0`، وهو HEAD المحلي وقت الفحص.

1. **حي، قراءة فقط:** صفحة التسجيل بالمتصفح، صحة الإصدار، واستجابات روابط الشريك. `/partner/coverage` يعرض 404، بينما `/partner/settings` و`/partner/shipments` يعيدان الزائر إلى الدخول (307).
2. **محلي، خدمات فعلية:** قاعدة PostgreSQL 16 جديدة، مهاجرات المشروع الحقيقية، حسابات اصطناعية، ومحاكي شركة يستقبل HTTP على loopback. خدمات التسعير/الطلبات/التوقيع لم تستبدل بمحاكاة برمجية؛ المحاكاة تخص الشركة الخارجية فقط.
3. **محلي، HTTP فعلي:** التسجيل والدخول، حفظ الإعدادات، إضافة المناطق والأسعار، اعتماد الإدارة ونشرها، تفعيل/تعطيل التاجر، أزرار حالات الشحن وWebhook. تستخدم الاختبارات طلبات النماذج الخلفية وليست نقرات متصفح شاملة لكل شاشة.
4. **مراجعة كود:** الصلاحيات، الجغرافيا، حالات الفشل، COD، الإلغاء، الجوال والتحديث الحي.

لم نختبر حساب شركة حقيقي أو مفاتيحها أو مهام الإنتاج أو صلاحيات جميع الأدوار أو النشر الإنتاجي أو استقبال Webhook حقيقي من شبكة شركة خارجية. لم يُنفذ اختبار ضغط أو انقطاع ميداني أو تدقيق اختراق شامل. إعداد `PLATFORM_DELIVERY_ENABLED` الحي لم يُقرأ أو يُغيّر؛ وجود العلم في الكود لا يثبت تفعيله في الإنتاج.

## العوائق المثبتة والإصلاح المطلوب

### 1. صفحة المناطق تُستبعد أثناء بناء الإنتاج — أولوية إطلاق

الصفحة موجودة ومتتبعة في Git منذ `0865569`:
`merchant-os/src/app/partner/coverage/page.tsx`.

لكن `.dockerignore` في جذر الريبو يتضمن `**/coverage` (السطر 11)، فيستبعد أيضاً مجلد الصفحة وليس تقارير الاختبارات فقط. البناء الإنتاجي ينسخ `merchant-os/` بعد تطبيق هذا الاستبعاد. فشل اختبار `COPY` لملف الصفحة مع أن الملف موجود محلياً، والنسخة الحية تعرض 404. كذلك يوجد استبعاد Git واسع قد يخفي المسار عن بعض أدوات البحث؛ الملف نفسه متتبع بالفعل.

**الإصلاح:** تضييق استبعاد تقارير التغطية لمساراتها الفعلية أو استثناء مسار الصفحة بوضوح، ثم بناء صورة الإنتاج واختبار الرابط من داخلها. لا يكفي نجاح `next dev` أو إعادة deploy للصورة بنفس قواعد الاستبعاد.

### 2. المناطق والأسعار غير محكومة بما يكفي

- `C02`: إرسال `centerLat/centerLng/radiusKm` إلى نموذج المنطقة لا يحفظها؛ القيم تبقى null. النموذج يعرض المدينة والاسم والزمن فقط.
- محرك العروض يفحص دائرة التغطية عندما تكون الإحداثيات ونصف القطر موجودة، ولا يطبق قيداً جغرافياً بهذه الطريقة إن غابت. لذلك اسم المدينة وحده لا يضمن رفض وجهة خارج المدينة.
- `C04`: قَبِل نموذج الأسعار `serviceAreaId` يعود إلى شريك آخر، وربط به سعراً للشريك الحالي. هذا خلل تحقق ملكية يحتاج إصلاحاً قبل إتاحة الخدمة.
- `C03`: السعر السلبي لم يُحفظ بفضل حماية قاعدة البيانات، لكن الرفض ظهر كخطأ خادم، وليس رسالة تحقق مناسبة للمستخدم.
- الواجهة الحالية توفر إضافة وحذفاً، ولا توفر تحريراً وتعطيلاً واضحين للسجلات المستخدمة. يجب حماية السجلات المرجعية بدلاً من حذفها بلا سياسة تشغيلية.

**الإصلاح:** حدود منطقة محفوظة وقابلة للمعاينة، قواعد تحقق خادمية، مطابقة ملكية المنطقة للشريك، منع نشر قاعدة غير مكتملة، ورسائل أخطاء وتعديل/تعطيل مع سجل تغييرات. تحديد هل التغطية تشمل الاستلام والتسليم معاً؛ الخوارزمية الحالية تفحص الوجهة فقط.

المصدر: `merchant-os/src/app/partner/coverage/page.tsx`، ودالة `quotePlatformDelivery`.

### 3. توقيف الشريك لا يوقف جميع صلاحياته

- `U04`: بعد إيقاف الشركة في قاعدة البيانات، جلسة الدخول السابقة استمرت في فتح إعداداتها. الدخول الجديد يُرفض بنجاح (`U05`).
- `Q06`: عرض قديم قُبل بعد إيقاف الشركة، وأنشأ شحنة.
- `W06`: Webhook صحيح التوقيع يستمر في تغيير حالات شركة موقوفة ما دام إعداد الربط فعالاً.

**الإصلاح:** إعادة التحقق من عضوية المستخدم وحالة الشريك على الطلبات الحساسة، وإبطال/تجديد صلاحيات الجلسات. فصل «وقف الطلبات الجديدة مع إكمال القائم» عن «تجميد أمني كامل»؛ اختبارات الإيقاف الحالية تفترض التجميد الكامل، ويجب تثبيت السياسة قبل التطبيق.

المصدر: `merchant-os/src/lib/auth/delivery-partner.ts`، `auth/config.ts`، وخدمات التوصيل.

### 4. قبول العرض لا يعيد فحص الحالة الحالية للطلب

`Q07`: أنشئت شحنة لطلب أُلغي بعد إصدار العرض. فحص حالات الطلب موجود عند إصدار العرض، لكنه غير كافٍ عند قبول عرض سابق. وينقص إعادة التحقق من اتصال التاجر، نشر التطبيق، وصلاحية إعداد الربط وقاعدة السعر.

**الإصلاح:** إعادة التحقق داخل نفس المعاملة وقت القبول، مع حماية التزامن. تُحفظ رسوم العرض لمدة محددة بسياسة معلنة، وتُرفض الأهلية المنتهية دون ترك شحنة أو عهدة مالية جزئية.

المصدر: `delivery-operations.service.ts:137` وما بعدها.

### 5. تعطل API قد يترك شحنة بلا إرسال ولا إعادة محاولة

- `Q08`: رد المحاكي 503؛ بقيت الشحنة REQUESTED ومرجع الشركة null، ولم تُنشأ مهمة إعادة محاولة دائمة. السجل النصي يقول إنها queued، لكنه ليس صف مهام فعلياً.
- `Q09`: إعداد شركة غير فعال لم يمنع قبول العرض؛ خرج قبول ظاهري دون إرسال.
- `Q11`: طلب بلا `branchId` حصل على عرض باستخدام الفرع الرئيسي، لكن بيانات الاستلام المرسلة للشركة لم تتضمن إحداثيات ذلك الفرع.
- `Q10`: إعادة إرسال الشحنة للمحاكي الداخلي تُغيّر مرجعه بدلاً من إعادة نفس المرجع.

**الإصلاح:** صف إرسال دائم بعد المعاملة، مفتاح عدم تكرار ثابت، مهلة اتصال محددة، إعادة محاولة بتأخير وحد أقصى، قائمة فشل تحتاج تدخل الموظف، ومصالحة مع الشركة. توحيد مصدر عنوان الاستلام بين التسعير والإرسال. إن أُريد تشغيل يدوي بلا API، يكون وضعاً صريحاً لا نجاحاً صامتاً.

المصدر: `delivery-operations.service.ts:220`، `partner-integration.service.ts:9`.

### 6. حالات الشحن لا تتحمل التكرار أو التأخير

- `W03`: الشحنة DELIVERED رجعت ASSIGNED عندما وصل حدث قديم؛ الطلب بقي DELIVERED.
- `W04`: نفس الحدث أضاف سجلين بدلاً من اكتشاف التكرار.
- `W05`: إشعار DELIVERED لطلب NEW جعل الشحنة مسلمة مع بقاء الطلب NEW، لأن خطأ عكس حالة الطلب يُبتلع.
- `W08`: مرجع شحنة غير معروف حصل على HTTP 200 و`success:true` دون معالجة فعلية.

**الإصلاح:** مخطط انتقالات موحد للشحنة والطلب، حماية الحالات النهائية، معرف حدث فريد، معالجة ذرية أو Inbox دائم قابل للاستئناف، وفصل «تم الاستلام للمعالجة» عن «تم التطبيق». الحدث غير المعروف يُعاد للمصالحة أو يُرفض بشكل متفق عليه؛ لا يضيع بصمت.

نجح رفض التوقيع الخاطئ (`W01`) وعزل مراجع الشحنات بين الشركات (`W07`). هذا لا يلغي خلل ملكية المناطق أعلاه.

المصدر: `partner-integration.service.ts:99`، و`partner/shipments/page.tsx`.

### 7. التسجيل وإعداد التطبيق

- `R04`: رقم هاتف مكوّن من حروف قُبل وأنشأ حساباً.
- `U03`: مكوّن الحقول يستخدم `type="url"` افتراضياً، واسم التطبيق لم يحدد نوع text. اختبار الحفظ الناجح احتاج قيمة على هيئة رابط كحل التفافي اختباري؛ هذا ليس صلاحية للواجهة الحالية.
- مراجعة الكود: عنوان API لا يُتحقق منه خادمياً بما يكفي، ولا توجد قيود واضحة على طلب عناوين داخلية. لا يوجد زر اختبار اتصال أو مهلة طلب. لم نختبر الوصول لشبكة الإنتاج الداخلية.
- مفتاح الربط يُحفظ مشفراً، لكن المفتاح نفسه يستخدم لاتصال API وتوقيع Webhook. التدوير والتعطيل وفصل الأسرار يحتاجان تدفقاً واضحاً.
- حفظ تعديلات تطبيق منشور لا يعيده تلقائياً للمراجعة؛ يلزم إصدار إعدادات معتمد إن كانت تغييرات حساسة.

**الإصلاح:** توحيد تحقق الهاتف، text للاسم، تحقق HTTPS والوجهات المسموحة وحماية طلبات الخادم، اختبار اتصال، تدوير آمن، ومعايير نشر صريحة.

## جوانب تشغيلية لم تكتمل

- البوابة جزء محمي داخل تطبيق Next.js الحالي، وليست خدمة أو مستودعاً منفصلاً.
- القائمة الجانبية مخفية تحت حجم lg ولا يوجد بديل تنقل جوال في تخطيط الشريك الحالي؛ تحتاج معالجة.
- شاشة الشحنات تعرض آخر 100 فقط، دون بحث أو ترقيم صفحات أو فلاتر تشغيل مناسبة، والحالات الخام بالإنجليزية.
- لا توجد آلية تحديث دوري/اشتراك واضح في شاشة شحنات الشريك. نجاح التحديث في قاعدة البيانات لا يثبت وصوله فوراً لكل نافذة مفتوحة لدى الشريك والتاجر والعميل.
- إسناد ASSIGNED لا يختار مندوباً فعلياً. نماذج المندوبين والإثبات والتحصيل موجودة، لكن ذلك لا يساوي شاشات وخطوات تشغيل مكتملة.
- لا يوجد في محول `PARTNER_HTTP_V1` الحالي استدعاء إلغاء أو استعلام مصالحة، رغم ذكر الإلغاء في نص إعداد التكامل. تعريف سياسة FAILED/CANCELLED وإعادة الإسناد والإرجاع ضروري.
- التوصيل عبر عروض المنصة يدعم CASH فقط حالياً. التحويل البنكي/ماي كاشي لهذا المسار ليس جزءاً مكتملاً؛ لا يجب الخلط مع توصيل التاجر نفسه.
- COD ينشئ «المبلغ المتوقع» فقط. يلزم إثبات التحصيل الفعلي، المطابقة، فروقات النقد، المستحقات والتسويات ومسؤولية المراجعة. لا تُغيّر العهدة تلقائياً إلى «تم التحصيل» بمجرد إشعار التسليم.
- زر الشريك التجريبي في الإدارة ينشر محاكياً ACTIVE/PUBLISHED؛ لا تستخدمه في الإنتاج باعتباره مخفياً عن التجار. الفحص الحالي لم يستخدمه هناك.
